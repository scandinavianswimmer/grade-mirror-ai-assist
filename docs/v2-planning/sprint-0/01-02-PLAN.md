# Plan 01-02 — Security & migration hardening + JWT auth helper

## Objective
Make the project safe to demo and reproducible: collapse the non-replayable migration history into one clean baseline, close the privilege/paywall-escalation hole on `users`, encrypt LMS tokens, stop trusting client-supplied identity, and remove the committed `.env`. Also ship the shared `getUserFromJWT()` helper that 01-03 depends on.

## Context
Per [../06-supabase-security-review.md](../06-supabase-security-review.md): migrations are non-replayable (duplicate `podcast_episodes CREATE TABLE` in `20250711194357` + `20250711194416`; conflicting `users.id` in `001_initial_schema.sql` vs `20250629180152`; `update_updated_at_column()` defined after first use; `enterprise_contacts`/`teacher_interest` live but absent from migrations). `users` UPDATE policy lacks `WITH CHECK`. `lms_integrations.access_token`/`refresh_token` are plaintext. `increment-feedback-count` trusts a body `userId`. `.env` is git-tracked and missing from `.gitignore`.

</action>

<task id="01-02-2">
<title>Close privilege escalation on users + encrypt LMS tokens</title>
<read_first>
- supabase/migrations/  (the new baseline from 01-02-1 — edit policies there)
- src/integrations/supabase/types.ts  (users + lms_integrations columns)
- docs/v2-planning/06-supabase-security-review.md  (RLS findings table)
</read_first>
<action>
In the baseline: add `WITH CHECK (auth.uid() = id)` to the `users` UPDATE policy, and prevent client writes to privileged columns `plan`, `role`, `weekly_feedback_count`, `last_reset_date` — either by `REVOKE UPDATE (plan, role, weekly_feedback_count, last_reset_date) ON public.users FROM authenticated` (column-level) or by moving those mutations behind a `SECURITY DEFINER` function callable only with service role. Add `WITH CHECK` to every other write/`FOR ALL` policy that lacks one. Restrict `ai_model_health` SELECT to service role (remove `USING (true)`). For `lms_integrations`: store `access_token`/`refresh_token` encrypted at rest using Supabase Vault (`vault.create_secret`) or `pgsodium` — replace the plaintext `text` columns with a secret reference, and add `token_expires_at timestamptz`. Tighten function CORS off `*` to an allowlist constant.
</action>
<acceptance_criteria>
- `users` UPDATE policy text contains `with check`.
- A test as user A cannot UPDATE `plan` or `role` on their own `users` row via the anon client (operation rejected or column unchanged).
- `ai_model_health` SELECT as a normal authenticated user returns 0 rows (or permission denied).
- `lms_integrations` no longer stores raw token text — columns reference Vault/`pgsodium`; `token_expires_at` exists.
</acceptance_criteria>
</task>

<task id="01-02-3">
<title>Ship getUserFromJWT() helper and apply it (kill body-supplied userId)</title>
<read_first>
- supabase/functions/create-class/index.ts  (correct auth model to mirror: auth.getUser(token))
- supabase/functions/increment-feedback-count/index.ts  (currently trusts body userId)
- supabase/functions/_shared/ai-router.ts  (shared-module conventions)
</read_first>
<action>
Create `supabase/functions/_shared/auth.ts` exporting `getUserFromJWT(req): Promise<{ userId: string }>` that reads the `Authorization` bearer, calls `supabase.auth.getUser(token)`, and throws a 401-style error if absent/invalid. Refactor `increment-feedback-count` to derive `userId` from `getUserFromJWT(req)` and IGNORE any `userId` in the body. Add a guard to the service-role functions (`anonymize-student-data`, `cleanup-training-data`, `scheduled-privacy-tasks`) requiring either a valid admin JWT or a shared cron secret header before running. (The grading function adopts this helper in 01-03.)
</action>
<acceptance_criteria>
- `supabase/functions/_shared/auth.ts` exists and exports `getUserFromJWT`.
- `increment-feedback-count/index.ts` no longer reads `userId`/`user_id` from the request body (grep confirms); it calls `getUserFromJWT`.
- Calling `increment-feedback-count` with a body `userId` for a different user does not affect that other user (identity comes from the JWT).
- Service-role functions reject calls lacking the admin JWT / cron secret.
</acceptance_criteria>
</task>
